# Win32 live-run matrix — which apps *run*, measured on pixels

The live counterpart to `W32APP_PLAN.md` W32A-18's binding matrix
(`docs/win32.md` tells what the personality *binds*; this file tells what
*runs*). Per `docs/plans/W32RUN_PLAN.md` D-WR2, this matrix is the only
place a "runs" claim lives, and every cell cites a live gate or a named
reason. The evidence protocol (pins, gates, frame digests) is
`docs/gui_receipts.md`.

What the six states mean:

- **binds** — the pinned binary's imports resolve (no REFUSE, no TODO
  fall-through). The W32APP half, re-stated here so the row reads whole.
- **enters** — it survives CRT startup to its first window on the live
  OVMF framebuffer (no early fault, no early exit).
- **draws** — it paints client content on pixels, not just a frame.
- **main UI** — its primary window or dialog reaches the working state,
  asserted over `screendump` pixels by `tools/fb_oracle.py`.
- **core task** — its defining job completes: PuTTY drives sessions,
  7-Zip lists/navigates/extracts, Notepad++ types/saves — byte- or
  pixel-asserted by the phase gate.
- **live net** — a live network flow completes against an in-lane server
  (`N/A` where the app has no live-net surface: offline by design, not
  silently untested).
